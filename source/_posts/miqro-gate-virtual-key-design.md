五十个账号,五十条并发流式请求,这是首版的设计基线。

一家公司只有五十个开发者用 AI 编程工具,却要为一件事吵上一整天:API Key 放在谁那里。

放在共享文档里,离职的人带走一把,公司要为这个人的用量付钱。放在每个人自己的口袋里,财务不知道钱花在哪,管理员想吊销一把,得知道它当初发给了谁。放在服务器上,那台服务器的 SSH 密码会变成整个公司的秘密。

我想了很久,最后决定写一个网关。把真实的 Key 锁在里面,外面的人只拿到虚拟的。

<!-- more -->

## 问题不是钥匙,是钥匙的副本

AI 编程工具的调用链是这样的:Claude Code 这类客户端要连供应商的 API,就需要一把 API Key。企业内部几十个人各自注册账号,每把 Key 都属于一个人。这带来四个问题:

- **不能轮换**。Key 要定期换,但换一把等于通知所有在用的人,流程一拖就是几个月。
- **不能吊销单个人**。一个人走了,那把 Key 还在各种 CI 配置里躺着,不知道谁在用。
- **成本无法归属**。月底账单出来,只有一个总额。哪个项目花的、哪个供应商花的,查不到。
- **没有边界**。拿到 Key 就等于拿到全部额度,没有"这个 Key 只能调用这些模型"的说法。

这些问题有一个共同根源:使用凭证和管理凭证用的是同一个东西。真实 Key 既是身份的证明,又是权限的载体。

解法在数据库领域很常见,叫虚拟化:给每个使用者发一张"虚拟凭证",它有自己的生命周期,可以签发、可以轮换、可以吊销;背后绑定的真实凭证由系统保管,使用者永远看不到。

MiQroGate 就是做这件事的。

## 核心设计:一张固定绑定的虚拟钥匙

首先明确一个边界:MiQroGate 不是智能路由平台,也不是模型聚合中转站。

它不做"把请求路由到最便宜的模型"这种事,不做模型映射,不做协议转换。那些是 CC Switch 的职责。MiQroGate 只做一件事:识别虚拟钥匙,换成真实钥匙,转发,记账。

每张 Virtual Key 固定绑定三样东西:一个项目、一个供应商产品、一个真实凭证。绑定是固定的,不存在"一张虚拟钥匙可以对应多个真实 Key"的情况。

这样设计是为了让账目干净。审计的时候,看到一张 Virtual Key 就知道它属于哪个项目、走哪个供应商、花了多少钱。如果做动态路由,审计线就断了——同一个请求,今天走这家明天走那家,成本归到谁的头上?

### Key 的格式

Virtual Key 长什么样?我们定义了一种 label-routing 格式:定长、严格 base64url,前半段是公钥 ID,后半段是密钥本体。

```
vkey_[public_key_id]_[secret]
```

用公钥 ID 做查表,用密钥本体做校验。这样网关收到一个 Key,先查表找到它的记录,再做常量时间 HMAC 校验,确认这把 Key 是真的、没被吊销。

### 生命周期

一张 Virtual Key 的一生是这样的:

1. **签发**。用户在门户里自助创建,系统生成新的密钥对。如果管理员给这个项目授权过,不需要审批。
2. **使用**。把 `Base URL` 和 Virtual Key 填进客户端,网关负责替换成真实凭证。
3. **轮换**。管理员可以随时轮换,旧 Key 立即失效,不影响真实凭证。
4. **吊销**。一个按钮,所有用这把 Key 的地方同时失效。

真实凭证可以有多版本。供应商那边换 Key 时,先签发新版本,验证没问题,再撤销旧版本,中间的流量不受影响。

## 数据面:一条不能拖慢的路径

网关的热路径是一行代码都不能多的地方。请求从这里经过,一次往返。

我们用 Spring WebFlux 写数据面。选它的原因很直接:这是纯 I/O 密集的转发路径,Reactor 的响应式模型能让单线程处理大量并发连接;阻塞代码在 event loop 上跑一次,整个网关的吞吐就塌一次。

转发管线分七步,每一步都有明确约束:

**1. 认证。** 从请求里取凭证头。恰好一个(`Authorization`、`x-api-key`、`api-key` 三选一)才继续;零个或者多个,直接 401。然后解析 Virtual Key——格式不对、公钥 ID 查不到、HMAC 校验失败、标签和绑定不匹配,全部返回同一个 404。

这里有一个刻意的设计:**失败原因不可区分。** 探测者永远无法通过响应差异判断一把 Key 是存在、被吊销还是格式错误。探测网关这件事,在响应层面得不到任何信息。

**2. 缓冲与预检。** 请求体进内存缓冲,有上限,超限返回 413。同时预检请求里的模型名是否在这把 Key 的允许列表里,不在就 403。注意,这一步在认证之后做——先用 404 挡住无效 Key,再用 403 挡住越权模型,错误的语义不会串。

**3. 缓存(可选)。** 默认关闭。打开缓存需要两把开关:Key 级别的 opt-in,外加请求里显式的缓存头。命中时按字节原样重放,包括 SSE 流。这是 ADR-0008 的决策:第一版不做缓存,但把接口留好,等流量模型清楚了再启用。

**4. 转发。** 解析上游地址,注意这一步做了 DNS 校验——防止网关变成 SSRF 代理。然后从数据库取出真实凭证,在 event loop 之外的线程池里解密(解密是 CPU 操作,不能占 event loop),注入请求头,把请求原样发给供应商。

转发时有一个细节:请求体的字节是原样保留的。不做任何解析、不重组,免得两边格式不一致。query string 也原样带过去。

**5. SSE 透传。** 流式响应边读边转给客户端。响应缓冲不做任何改动。

**6. 用量观察。** 这是全文最微妙的地方。SSE 流里嵌着 usage 数据,我们需要它,但供应商的流是连续的。做法是:观察器拷贝一份有界的数据流(单条事件最大 256KB,最多保留 10 条观察),从中提取 token 数,原始缓冲不做任何修改、不保留任何内容。

**7. 记账。** 每个到达上游的请求,先写一条 `IN_FLIGHT` 记录,结束时恰好补一次完成记录。客户端取消、上游报错,也必须补上——不能让一条记录永远挂在"进行中"。

## 安全:把"不做什么"写进设计

这个项目的安全设计,大部分内容不是"做了哪些防护",而是"决定不做什么"。

**不保存提示词、代码和回答正文。** 网关是转发器,不是记录器。用量数据从流里提取完就丢,正文一个字节都不落盘。这也是数据面敢放 Docker Compose 交付的原因——它本身没有值得偷的东西。

**不因预算阻断请求。** 额度超了,不发 429,发 webhook 告警。理由是:生产环境里一个开发者的请求被突然掐断,损失比超预算大得多。告警让人处理,阻断让机器处理,这里选择前者。

**管理面和数据面分离。** 控制面跑 8080,网关跑 8081。网关端口只暴露 `health` 和 `info` 两个管理端点,`metrics`、`prometheus` 一律不开放,有冒烟测试守着这条边界。

**密钥零残留。** 解析出的 Virtual Key 密钥本体,在函数的所有退出路径上都会被覆写为零。这个叫 SecretWiping,写进了每个入口的调用链。

**许可证白名单。** 生产依赖只允许 Apache-2.0、MIT、BSD 这类宽松许可证。这是个没人注意但很重要的约束——企业部署的合规底线。

## 工程的另一半:谁写的代码

MiQroGate 有一个特殊的地方:需求与设计基线由规划阶段完成,之后的代码由 Claude Code 按 Goal 逐条实施。

规格作者(项目所有者)写文档,不写代码。Claude Code 读规格、实现、测试、更新文档、提交、推送。项目所有者负责审查、合并、发布。

这个模式跑通了,但它不是"AI 替我写代码"这么简单。它逼出了两样东西:

**文档必须精确。** 三十多份文档:产品需求、系统架构、领域模型、数据库 Schema、API 契约、Provider 适配器契约、安全设计、部署运维、测试验收。代码里任何一个含糊的地方,写代码的 Agent 都会卡住,而它不会来问人,它会照着文档里最接近的意思写。含糊的代价从"讨论一下"变成了"返工一次"。

**验收必须自动化。** 没有人的耐心去逐条验证 Agent 的产出,所以测试是全自动的:单测、契约测试、架构测试(ArchUnit 管模块边界)、协议测试夹具、端到端。最近一个 Goal 结束时,vitest 21/21、Playwright 15/15,lint、typecheck、构建全绿。

还有一些工程细节值得记录:CI 拒绝所有不带 `@sha256:` 摘要的 Compose 镜像;Maven Wrapper 校验真实 SHA-256 校验和;Windows 下 `mvnw.cmd` 正确传递退出码——因为有一次构建失败被报告成了成功。

品牌名从 MiQroKey Gateway 改名为 MiQroGate 的那天,历史被压成一次提交重新发布,旧的本地 bundle 备份。项目的公开版本从一天开始算。

## 现状

Phase 1 进行中。核心闭环已经打通:Virtual Key 签发 → 网关路由与凭证注入 → 用量统计 → 用户门户,横跨控制面和数据面。

449 个 Java 文件,134 个测试文件。界面刚完成 TDesign 组件库迁移,前端测试全绿(vitest 21/21、Playwright 15/15)。

供应商适配器已经实现 7 家厂商 20 个产品,但都还没有经过真实凭证联调验证。文档里明确区分"官方资料确认 / 已实现 / 真实凭证已验证"三级,这是这个项目的一条规矩:**不伪造 PASS**。

从"Key 放在谁那里"这个问题,到一张可以签发、轮换、吊销、计量的虚拟钥匙,中间隔着一个网关,和三十多份文档。

网关还开着。钥匙在柜子里。五十个账号的问题,现在由一行配置回答。

## 附:设计决策速查

| 问题 | 决策 | 理由 |
|------|------|------|
| 虚拟 Key 能不能多绑 | 固定绑定一个项目+供应商+凭证 | 审计线清晰 |
| 认证失败怎么响应 | 统一 404 | 防探测 |
| 超预算怎么处理 | Webhook 告警,不阻断 | 生产不掐请求 |
| 缓存开不开 | 默认关,opt-in | 流量模型未明 |
| 正文存不存 | 不存 | 数据面没有可偷的东西 |
| 网关端口开什么 | health/info | 冒烟测试守护 |
| 协议转换做不做 | 不做,交给 CC Switch | 边界清晰 |
| 依赖 LiteLLM 吗 | 不依赖 | 运行时零第三方依赖 |
