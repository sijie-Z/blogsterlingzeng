手机首屏有两个大资源。

首页横幅，亮色原图 63KB，尺寸 1920×1080。Live2D 主纹理，PNG 1.7MB，尺寸 2048×2048。前者在 390px 宽的屏幕上按 100vw 显示，后者在 200px 的画布里渲染。

两个数字都不在正文里，但都出现在首屏。它们浪费的是同一类东西：用不到的像素。

## 横幅：三档尺寸，让浏览器自己选

原图保留 1920，另生成 1280 和 960 两档 WebP：

```html
<img
  src="/images/banner-light.webp"
  srcset="/images/banner-light-960.webp 960w,
          /images/banner-light-1280.webp 1280w,
          /images/banner-light.webp 1920w"
  sizes="100vw"
  width="1920" height="1080">
```

`sizes="100vw"` 告诉浏览器图片占满视口。390px 宽、DPR 3 的手机需要 1170 个物理像素，浏览器选 1280 档；桌面 1440px、DPR 1 需要 1440，选 1920 档。选哪一档由浏览器算，不需要前端判断 UA。

四季切换是另一条路径。切换季节时 `img.src` 会变，但只改 `src` 不改 `srcset`，浏览器仍按旧候选选图。`setBannerSrc()` 同时写两个属性：

```js
function setBannerSrc(img, url) {
  const base = url.replace(/\.webp$/, '');
  img.srcset = `${base}-960.webp 960w, ${base}-1280.webp 1280w, ${url} 1920w`;
  img.src = url;
}
```

还有一个容易漏的地方：横幅容器同时有 `background-image`。图片节点已经按 srcset 选好尺寸，容器再设一次背景，会把 1920 原图也下载一遍。现在只在容器没有 `img` 子节点时才设背景。

| 资源 | 原始 | 手机实际 | 触发条件 |
|---|---|---:|---|
| 亮色横幅 | 63KB / 1920 | 35KB / 960 | 390px、DPR 1–2 |
| 亮色横幅 | 63KB / 1920 | 50KB / 1280 | 390px、DPR 3 |
| 暗色横幅 | 153KB / 1920 | 87KB / 960 | 390px、DPR 2 |
| 秋季横幅 | 273KB / 1920 | 141KB / 960 | 390px、DPR 1–2 |

## 纹理：2048 到 1024

Live2D 主纹理是 2048×2048 PNG，1,768,051 字节。模型在页面上只有 200×200，Retina 屏按 2 倍算也只有 400px。2048 的纹理在这个尺寸下是 5 倍超采样。

重采样到 1024×1024 并转成 WebP：

```json
"Textures": [
  "textures/texture_00.webp",
  "textures/texture_01.png"
]
```

文件从 1,768,051 字节降到 308,352 字节，少了 83%。清晰度没有可见变化：1024 对 200px 画布仍然是 5 倍余量，眼睛和发丝的边缘在截图对比里一致。

保留原 PNG 不是犹豫。Live2D 的 `index.json` 会被浏览器缓存，GitHub Pages 默认 10 分钟。旧缓存里的 `index.json` 还指向 PNG，如果部署时直接删掉，这段时间内模型会缺纹理。默认保留 PNG 作为回退；确认缓存过期后，可以用 `CJ_SKIP_OLD_TEXTURES=1` 构建，把 1.7MB 从部署产物里移除。

另一张 `texture_01.png` 只有 90KB，1024×1024，转 WebP 的收益不到 60KB，保持原样。

| 资源 | 原始 | 现在 | 节省 |
|---|---:|---:|---:|
| Live2D 主纹理 | 1,768,051 B | 308,352 B | 83% |
| 副纹理 | 90,177 B | 90,177 B | 0% |
| 手机横幅（亮色） | 63KB | 35KB | 44% |
| 手机横幅（秋季） | 273KB | 141KB | 48% |

## 同一条原则

横幅按视口宽度 × DPR 选图，纹理按画布显示尺寸重采样。两条链路不一样，判断标准一样：这个资源在屏幕上最多显示多大，就交付多大的像素。

反过来也成立。截图、文字图、需要放大查看的照片，不应该按显示尺寸重采样。用户会双击放大，会保存原图，会拿去做别的用途。这些资源要保留原始分辨率，优化只能换编码，不能降尺寸。

## 边界

这轮没有动 `texture_01.png`，也没有把横幅统一压到 960。前者收益小于维护成本，后者会在 1440px 桌面上产生可见的放大模糊。优化的目标是去掉用不到的像素，不是把所有数字压到最小。

回到开头：63KB 的横幅在手机上只需要 35KB，1.7MB 的纹理只需要 308KB。两个数字加起来，首屏少下载约 1.4MB。没有改一行业务代码。
